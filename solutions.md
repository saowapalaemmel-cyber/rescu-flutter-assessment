# 1. Part A — Bug tickets and  Part B — Features

## Part A
### RES-101 · Search shows results for the wrong query
- **Root cause:** Every keystroke started an independent request, and each response wrote into the same `results` with nothing tying it to its query. `FakeApiService.searchDeals` latency grows as the query gets shorter (about 1.1-1.4 s for `s`, 180-480 ms for `sushi`), so older short queries finish after newer long ones and overwrite their results.
- **Fix:** [SearchDealsController](lib/feature/search/search_deals_controller.dart) assigns each input change a generation number; results, error logging and `isLoading` are updated only if the generation is still current. A 300 ms debounce reduces requests, but the generation guard is the core fix: it prevents any response from an earlier query from overwriting the latest query, even when that older request is already in flight and cannot be cancelled.
- **Alternative rejected:** Compare the response query to the current text field value before assigning results. This couples the controller to UI state and still requires separate guards for loading and errors; a generation token keeps all request side effects associated with the same query lifecycle.
- **Edge cases considered:** Rapid typing, clearing the query while a request is pending, and closing the controller with a debounce or request in flight; the generation check and timer cleanup cover these cases. A useful follow-up would be showing a user-facing error and offering retry when the current request fails; currently failures are logged.

### RES-102 · Crash after leaving My orders
- **Root cause:** `PickupCountdown` (`lib/feature/order/widget/pickup_countdown.dart`) starts a `Timer.periodic` in `initState()` and discards the returned `Timer`, so nothing can ever cancel it. Leaving My orders disposes the `State`, but the timer keeps firing and its next tick calls `setState()` on a disposed State.
- **Fix:** Store the timer in `late final Timer _timer` and call `_timer.cancel()` in `dispose()` before `super.dispose()`. This is the right fix because the timer is owned by the widget State, so cancelling it at that State's disposal stops the callback at its source and matches the timer's lifetime to the UI it updates. (Safe as `late final` because `initState()` always assigns it.)
- **Alternative rejected:** Check `mounted` before calling `setState()`. That avoids the assertion but leaves the periodic timer running after navigation, wasting work and masking the lifecycle leak instead of stopping the callback source.
- **Edge cases considered:** Leaving via back navigation or route removal cancels the timer with the widget State. If `pickupStart` changes while this State is mounted, the next tick reads the updated value. A useful follow-up would be stopping the timer once the pickup window opens, since it currently continues ticking even though the displayed text no longer changes.

### RES-103 · Requests pile up the longer you browse
- **Root cause:** `DealDetailsController.onInit()` calls `ever(cartService.itemCount, (_) => _recheckAvailability())` and discards the returned `Worker`. `cartService.itemCount` lives for the whole session, so every details controller stayed subscribed after its route closed. One Add to bag changed `itemCount` and fired every old callback, each calling `dealRepo.fetchById(deal.id)`: one `GET /deals/:id` per deal viewed.
- **Fix:** Keep the worker in `Worker? _cartWorker` and call `_cartWorker?.dispose()` in `onClose()`. This is the right fix because it releases the actual subscription that outlives the details route; the controller still rechecks availability while its screen is active, but cannot issue requests after it closes. Confirmed with a temporary `onClose` log that the controller is disposed on pop.
- **Alternative rejected:** Skip the recheck unless this is the current route. That may suppress the extra requests, but leaves closed controllers subscribed to the app-wide cart and retained for the session; disposing the worker fixes the lifecycle leak rather than hiding its effects.
- **Edge cases considered:** Opening several deal pages and then adding from the current page; each closed controller disposes its own cart worker, while the active page continues to recheck stock. Useful follow-ups are guarding an in-flight availability response after the details controller closes and handling fetch failures explicitly; those cases are not covered by this fix.

### RES-104 · Duplicate deals in the home feed
- **Root cause:** A page request can remain in flight while a refresh replaces the feed. If that older pagination response is appended after the refreshed first page, overlapping items can appear more than once, and the feed can exceed the catalog size.
- **Fix:** `HomeController` uses `_feedGeneration` to identify the current feed request generation. A refresh advances the generation; pagination responses only append when their captured generation is still current. A successful refresh also invalidates pagination started during that refresh before replacing `deals`, `_page`, and `_totalPages`. `_isFetchingMore` prevents concurrent pagination requests. This is the right fix because it prevents stale responses from mutating the refreshed feed at the point where the race occurs, rather than trying to repair duplicate data after it has already been applied.
- **Alternative rejected:** Deduplicating by deal ID after each response. It may hide repeated cards, but a stale response can still overwrite pagination state or append outdated page data after refresh; generation validation rejects the obsolete response entirely. Clearing `deals` at refresh start was also avoided because it causes unnecessary empty-feed flicker and discards visible content if refresh fails.
- **Edge cases:** Stale page responses are ignored after refresh; pagination errors are logged, and the loading indicator is completed. A dedicated automated race test for simultaneous refresh/load-more is not present, so the concurrency behavior still needs a regression test with controllable request completion order.

### RES-106 · Wrong pickup times; "Pickup today" filter misses deals
- **Root cause:** The API provides UTC instants, but pickup labels and the day filter must use the market's calendar and clock. Treating UTC dates as local market dates makes a 06:00 Bangkok pickup appear on the previous UTC date; formatting without first converting to the market timezone can also show the wrong hours.
- **Fix:** `PickupWindowModel` converts instants to the market's UTC+7 time before formatting labels and deciding whether a window overlaps today. `isTodayAt(DateTime now)` accepts the current time as an argument so date-boundary behavior can be tested deterministically. This is the right fix because both display and filtering use the same market-local interpretation of the API instants, including windows that cross UTC dates.
- **Alternative rejected:** Relying on the device timezone. Users whose devices are set to another timezone would see different pickup labels and potentially different “today” results; using the market timezone makes behavior consistent with the stores' actual pickup schedule.
- **Edge cases:** Tests cover the reported 06:00–09:30 example, a slot on a different market day, and an overnight window overlapping the day it ends. The market offset is intentionally fixed; adding markets with different or daylight-saving timezones would require timezone-aware configuration rather than this constant offset.

### RES-107 · Deep link opens to a crash
- **Root cause:** Opening a deal from the feed passes a `DealModel` through `Get.arguments`, but a deep link only supplies query parameters such as `id` and `source`. A details screen/controller that assumes the model argument exists dereferences null on the deep-link route.
- **Fix:** `DealDetailsController.onInit()` accepts a `DealModel` argument when navigation comes from the app. Otherwise, it parses the `id` route parameter and fetches the deal through `DealRepo.fetchById()`. The details screen shows a loading state while the request is pending, then renders the fully populated deal; known invalid-ID, not-found, and malformed-response cases receive explicit error text. This is the right fix because it resolves the missing-model root cause by loading the actual deal identified by the link, so a valid link opens the same functional details page as in-app navigation.
- **Alternative rejected:** Requiring all callers to pass `Get.arguments`. External deep links cannot carry an in-memory `DealModel`, so this preserves the crash for the exact entry path RES-107 reports. Showing a generic fallback instead was also rejected because the ticket requires deal 42 to open as a working details page.
- **Edge cases:** Handles a missing/invalid ID, a not-found API response, and an invalid response format. The existing tests do not include an end-to-end deep-link navigation test for `rescu://open/deal?id=42&source=push`; verify both the in-app simulator and Android intent path manually or add a route-level regression test.

## Part B
### F-1 · Live flash-sale countdowns
- **Approach:** `FlashSaleService` runs one app-wide `Timer.periodic` (1 s) that updates a shared `now` value and flips a per-deal `RxBool` when that deal's deadline passes. `FlashSaleCountdown` wraps only its `Text` in an `Obx` that reads `now`, so each tick rebuilds the countdown text and nothing else. Cards and the flash rail read only the per-deal `expired` flag, never `now`, so they rebuild once, at expiry. The same widget is used in the flash rail, home feed cards and details screen, so the format (`mm:ss`, or `hh:mm:ss` above an hour) and the "Expired" state are consistent everywhere.
- **Expiry behavior:** When a countdown reaches zero, cards and the flash rail switch to a disabled "Expired" state and the details screen disables Add to bag. `CartService.add` also rechecks the deadline and returns `false`, so a tap that races the UI update is still rejected. `CartService` listens to the shared clock, so it removes expired deals from the bag even when the user is on another screen. It records a notice shown as a dismissible banner in the bag screen (which stays visible when the bag becomes empty), plus a snackbar when the user is not on the bag screen.
- **Why this is the right fix:** The number of timers stays constant with 100+ visible countdowns, and there are no per-card timers to cancel, which avoids the leak pattern behind RES-102. Scoping the per-second rebuild to the text widget meets the requirement that ticks must not rebuild whole cards or the list. Enforcing expiry in the service as well as the UI means correctness does not depend on the screen rebuilding in time.
- **Alternative rejected:** A `Timer.periodic` inside each card, or an `Obx` around each card driven by its own timer. With 100+ cards that means 100+ timers that each need correct cancellation on dispose, and an `Obx` around the card would rebuild the whole card every second, which the requirements forbid. A shared ticker with a text-only listener is simpler and cheaper.
- **Edge cases handled:** A deal already expired when first shown; expiry while the deal sits in the bag, even if the user is on another screen; a tap on Add to bag at the moment of expiry (rejected again in `CartService.add`); expiry while the user is on the bag screen (banner instead of snackbar); an empty bag after removal (the notice stays visible); returning from the background (remaining time is computed from the clock on every tick); 100+ visible countdowns (one ticker, text-only rebuilds).
- **Edge cases handled:** A deal already expired when first shown; expiry while the deal is in the bag, even on another screen; a tap on Add to bag at the moment of expiry (rejected again in `CartService.add`); an empty bag after removal (the notice stays visible); returning from the background (time is recomputed from the clock each tick).
- **Considered, not handled:** Device clock changes (the countdown trusts the device clock; fixing it needs a server time offset the fake API doesn't provide). Notices are dismissed by index, so a new notice arriving mid-dismissal could remove the wrong one (rare, so I accepted it). Rebuild scope was reasoned from the widget structure, not measured in DevTools.

# 3. Design Questions
### Q1: In this codebase, what is the difference between a `GetxController`'s lifecycle and a widget `State`'s lifecycle? Name one bug from Part A that exists because of confusion between the two.
A State lives from initState() to dispose() with its widget, while a GetxController is owned by GetX (onInit() to onClose(), usually when its route is popped) and can outlive a single widget. Each must release what it creates. RES-102 mixed this up: PickupCountdown never cancelled its Timer.periodic, so it kept ticking after the user left My orders and called setState() on a disposed State. Fixed by calling _timer.cancel() in dispose().

### Q2: When does wrapping a large subtree in a single `Obx` hurt you? How do you decide how tightly to scope reactivity?
An Obx rebuilds its whole builder when any observable inside it changes, so a large Obx makes a small change, like a countdown text, rebuild expensive children such as lists and images. I wrap only the smallest widget that reads each reactive value and keep static structure outside it. I decide the scope by tracing which widgets read each observable and checking rebuild counts in DevTools.

### Q3: How would you write an automated test that would have caught RES-106 before release? What (if anything) would you change in the code to make such a test possible?
I would write a unit test on `PickupWindowModel` using fixed UTC instants and a fixed `now`, asserting both the Bangkok label and `isTodayAt(now)`. The cases are the reported 23:00-02:30 UTC window (06:00-09:30 in Bangkok, on the previous UTC date), a different market day, an overnight window, and a boundary near local midnight. It should also run under a non-Bangkok timezone in CI (e.g. `TZ=UTC`) so it can't pass just because a developer's machine matches the market. The code already supports this: `isTodayAt` takes `now` as an argument and the UTC+7 offset is applied explicitly. A market with a different timezone or daylight saving would need timezone-aware configuration and its own cases.
